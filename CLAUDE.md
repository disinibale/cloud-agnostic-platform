# CLAUDE.md

Project memory for Claude Code. Read this before every task. `SPEC.md` describes the initial Phase 0 scaffold; this file holds the rules that apply for the life of the repo.

## What this repo is

A language-agnostic, cloud-agnostic platform engineering lab, built as an SRE / platform portfolio. **The platform is the product.** The three services are deliberately trivial workloads that exist to be deployed, observed and broken.

Any service in any language that follows the service contract (`docs/service-contract.md`) must be deployable with no platform changes. Node.js, Go and Python exist to prove that.

## Layout

```
services/orders/   Node.js + TypeScript + Express 5, pnpm, Vitest
services/users/    Go, standard library only
services/worker/   Python, uv, pytest, ruff
docs/              service contract, ADRs, (later) runbooks, SLOs, postmortems
Makefile           single entry point for everything
```

## Commands

```bash
make help                 # list all targets
make install              # install deps for every service
make lint                 # lint every service (must pass)
make test                 # test every service (must pass)
make fmt                  # format all code
make run-users            # Go users service on :8081
make run-orders           # Express orders service on :8080 (calls users)
make run-worker           # Python worker, reads JSON Lines from stdin
make -C services/<name> <target>   # one service only
```

Always run `make lint && make test` before saying a task is done.

## Who builds what

The owner is learning SRE by building the platform layers **by hand**. That is the point of the repo.

**Owner builds (do not write these unless explicitly asked in the current task):**
Dockerfiles, Kubernetes / Kustomize / Helm, kind config, CI workflows, the service contract implementation (`/healthz`, `/readyz`, `/metrics`, JSON logs, SIGTERM handling), queue integration, observability, SLOs and alerts, Argo CD, chaos experiments, Terraform.

For these areas, act as a **senior SRE reviewer**: explain concepts, review the owner's code, point out bugs and risks, suggest what to read or try. If asked "how do I…", explain the approach and trade-offs before offering code, and ask whether they want the code or want to write it themselves.

**Claude Code may build freely:** application code inside the three services, tests, tooling config (linters, formatters), Makefile targets, and docs the owner asks for.

## Hard rules

1. **Nothing fake.** No empty files, placeholder configs, `TODO: implement` stubs, or folders for future work. Every file must be complete and working.
2. **No overclaims.** The README and docs describe only what exists right now. Planned work lives in the README's Status table, labelled as planned. When something ships, update the table in the same change.
3. **Pin versions.** Exact versions, lockfiles committed, base images digest-pinned once they exist. Check the current stable release before adding anything.
4. **No AI residue.** No "Generated by…", chat-style sign-offs, or comments narrating your edits (`# Fix:`, `# Removed X`). Comments explain _why_.
5. **No borrowed names.** No employer, client or product names anywhere. Fake data uses `example.com`.
6. **No secrets.** No `.env` files, tokens or credentials committed. Config comes from environment variables.
7. **Stay in scope.** Do only what the task asks. Ideas go in `IDEAS.md`, not into the code. If something outside scope seems necessary, stop and ask.
8. **Keep services trivial.** In-memory data, no real auth or payments, no new business features. Reliability features (timeouts, retries, graceful degradation) are welcome.

## Service conventions

- Config only from env vars with sensible defaults (`PORT`, `USERS_URL`, `USERS_TIMEOUT_MS`, …). Document every new variable in that service's section of the README.
- JSON in, JSON out. Errors return a JSON body like `{ "error": "message" }` with the correct status code (`400` invalid input, `404` not found, `422` unknown reference, `502` dependency down).
- Every outbound call has an explicit timeout.
- `users`: standard library only, `log/slog`, concurrency-safe store, table-driven tests with `httptest`.
- `orders`: TypeScript strict, app factory (`app.ts`) separate from the listener (`server.ts`), Vitest + Supertest, dependencies mocked in tests.
- `worker`: processing logic separate from the event source so the source can be swapped (stdin today, a queue later). Never crashes on bad input; rejects it and continues.
- Every behaviour change ships with tests, including error paths.

## The service contract

`docs/service-contract.md` is the source of truth for health endpoints, metric names, label names, log fields and shutdown behaviour. All three services must implement it identically. Never change metric names, label names or log fields in one service only; change the contract doc first, then every service.
